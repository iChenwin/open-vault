# 产品与设计评审

以下为六个 AI 专家视角的结构化评审，不代表已邀请真人专家。目标是参考 Synology Active Backup for Business 的集中管理体验，独立开发开源 Linux 文件级备份管理工具，不复制商标、素材或专有代码。

参考：[Synology ABB 官方总览](https://www.synology.cn/zh-cn/dsm/feature/active-backup-business/overview)。其集中管理、计划、状态通知与多层次恢复构成产品参考；该产品包含更广泛的平台与工作负载支持，首版不作功能对等承诺。

## 产品岗位：三位专家视角

| 角色 | 主张 | 首版落点 |
| --- | --- | --- |
| 中小企业 Linux 管理员 | 首次部署和恢复必须可理解，任务失败不能被“已提交”掩盖 | 仓库状态、任务列表、恢复目录、操作记录同屏；异步任务明确区分运行中、成功、失败 |
| 备份产品经理 | 范围可控，比功能数量更重要 | Linux 文件级备份、周期计划、快照浏览、隔离目录恢复、仓库校验；复用 restic 加密及去重能力 |
| 恢复验收负责人 | 备份成功不能代替恢复成功 | 要求真实文件内容恢复测试；快照使用完整 ID；恢复后由管理员核对关键文件及应用可用性 |

## 设计岗位：三位专家视角

| 角色 | 主张 | 首版落点 |
| --- | --- | --- |
| 信息架构师 | 按“准备仓库 → 创建任务 → 运行 → 恢复 → 验证”组织 | 状态与范围、任务创建和列表、快照、操作记录 |
| 交互设计师 | 每个操作都要有反馈，恢复写入位置明确 | 接受后显示操作编号并自动刷新；恢复弹窗只接受新子目录名称；失败保留错误提示 |
| 可访问性设计师 | 关键状态不能仅依赖颜色，鼠标不应是必需条件 | 原生按钮和表单标签、文本状态、焦点轮廓、原生模态对话框、实时通知、窄屏单列与横向表格 |

## 分歧与共识

产品希望快速支持跨主机集中备份；恢复负责人认为首版应先证明本机文件可恢复。共识：首版服务运行在可直接访问源目录的 Linux 主机，控制台管理该服务的任务；远端 agent、多租户、虚拟机和裸机恢复列入后续路线，不在界面暗示已支持。

运营可能希望默认无人值守计划；管理员需要明确知道何时触发。共识：创建时展示以分钟计的间隔，可停用定时，保存后支持立即运行，展示最近尝试及独立操作结果。

设计希望首屏简单；技术要求暴露恢复和源目录边界。共识：将这两项作为固定范围卡片展示，不展示仓库密码；访问令牌只放 sessionStorage，不写入 URL，断开时清除。

## 首版界面与接口契约

纯原生 HTML/CSS/JS，无 CDN 或演示数据。所有服务端动态文案以 textContent 插入。界面使用同源 API 与 Bearer 访问令牌。连接后读取状态、任务、快照、操作记录，每五秒刷新。操作忙碌时禁用备份、初始化、校验及恢复操作；服务端仍须以 409 作为并发互斥的最终保证。

初始化、校验、手动备份和恢复返回 202 仅表示接受，最终结果以操作记录为准。仓库尚未初始化、配置错误、认证失效和服务器错误均明确反馈；认证失效返回连接页。空列表说明下一步，不填充虚构成功记录。

任务支持启用和暂停定时、删除任务；删除前明确提示保留已有快照。首版不支持修改源路径及间隔。恢复为所选快照的全量恢复，写入恢复根目录内的新子目录，暂无文件树选择。

## 验收标准

1. 无令牌无法读取受保护 API；断开后清除当前会话令牌。
2. 允许目录范围可见；创建任务对空路径、非绝对路径和无效间隔给出反馈，服务端继续进行完整校验。
3. 初始化、备份、恢复、校验从接受到完成都有可追踪记录，失败不显示为成功。
4. 能创建文件、备份、修改或删除源文件，再从完整快照 ID 恢复到新目录，并逐字节核对原始内容。
5. 恢复目标不得逃逸配置的恢复根目录，不直接覆盖原始源目录；服务端负责权限与路径安全。
6. 仓库校验结果可见；界面明确说明文件备份无法替代运行中数据库的一致性备份。
7. 全部主要功能可通过键盘使用；窄屏无页面整体横向溢出；服务端输入作为纯文本展示。

## 后续路线

优先补齐任务路径与间隔编辑、保留策略、失败通知、恢复文件选择与自动恢复验证；之后评估远端 agent、细粒度权限、应用一致性和可观测性。整机与裸机恢复需要独立设计、启动介质和硬件兼容验收。
