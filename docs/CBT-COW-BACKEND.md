# COW 后端改造边界

当前 CBT 备份尚未通过真实内核验收。[ov1 实验](https://github.com/iChenwin/open-vault/actions/runs/39565285985) 的 ext4 全量恢复与参考快照一致，增量恢复的整卷摘要不一致。ov2 已修正一处确认的 zero-write 漏跟踪，但不能据此认定全部差异已消除。

## 同卷 COW 的问题

固定上游驱动要求 COW 文件位于被跟踪卷内，并在快照及增量路径排除自己对 COW 文件的写入。读取快照时，未映射的块直接从原卷读取。因此 COW 自身的数据块可能既未进入增量索引，也不具备完整的时间点稳定性。已备份仓库的认证加密和重建摘要只能证明保存的数据完整，不能证明上游变更索引覆盖全部源变化。

当前实验保存差异块、旧索引映射值及 COW 的物理分配，区分已标记块重建错误、未标记普通块和 COW 自身范围。任何整卷差异仍判定失败。只读文件系统检查、文件清单或较少的源读取量均不能代替此条件。

## 不可直接放宽同卷校验

上游 `filesystem.c` 在 COW 文件句柄关闭后，使用 COW 的 FIEMAP 物理偏移执行原始 IO，但目标固定为源设备。若只删除 `file_is_on_bdev` 校验，外盘物理偏移会被应用到源盘。卸载和重新挂载逻辑也将源挂载与 COW 路径绑定；现有 Go 适配器同样据此验证和解析路径。

因此本版没有删除该校验，也没有启用未经验证的外置 COW。

## 后续实现范围

优先研究边界明确的外置文件后端，而不是承诺跨卸载或重启恢复：

1. COW 位于独立文件系统，分别固定源设备、COW 设备、挂载身份及文件身份。
2. 保持 COW 文件句柄，明确禁用该后端的原始设备 IO 回退，禁止将外盘偏移用于源盘。
3. 源或 COW 挂载变化、身份变化、IO 错误、空间耗尽均使跟踪失效；拒绝继续备份并保留诊断，要求新基线。
4. 同步改造配置、驱动状态、路径解析及持久化日志，不沿用同卷路径推断。
5. 外部驱动改动保留 GPL 许可及可复现源码差异，Go 控制台和仓库继续独立实现。

这需要驱动功能开发，并非配置开关。尚未实施或验收。

## 完成条件

在 Ubuntu 24.04 amd64 GA 6.8 的隔离环境对 ext4、XFS 分别完成全量和多次增量：同一快照重复读取稳定，重建与完整参考镜像逐字节一致，文件系统检查及文件清单通过，旧版本仍能脱离源盘恢复。另需覆盖持续并发写入、零写入、COW 增长、空间耗尽、IO 错误和两个挂载分别变化的失败路径。仍保持当前禁用 discard 的准入条件。

达到这些条件后才能更新功能状态；当前草稿 PR 和测试通过的用户态代码不代表此驱动方案已经可用。
