# V2 CBT 验证记录

日期：2026-10-21。CBT 实现现已更新到默认分支 `main`，开发分支为 `feature/linux-cbt`，审阅记录为 [PR #1](https://github.com/iChenwin/open-vault/pull/1)。

## 已完成的用户态验证

- Windows 全仓 `go test ./...`、`go vet ./...`。
- Linux 用户态单测：加密基线、按声明区间读取增量、父链重建、摘要校验、密文篡改拒绝、错误密钥、取消、发布失败、HEAD 持久性确认。
- 协调器测试：父代身份与序列在旋转前检查；提交完成但尚未调用驱动时可继续；驱动操作结果不确定时拒绝自动继续；提交数据损坏时保留快照。
- 驱动协议单测使用模拟 `/proc` 和固定命令执行器，验证代际、挂载、旧索引、重启状态和异常状态。它们不是内核驱动实测。
- Linux Unix socket 代理集成、后台服务异步串行/持久化/中断、真实子进程超时与进程组取消、0660 socket 权限与既有路径保护。该项使用测试 CLI，不证明内核能力。
- Chrome 无头浏览器以测试数据检查 1280px 桌面与 390px 手机页面，确认没有 JavaScript 运行异常，修复并验证窄屏页面无横向溢出。此项是界面验证。
- [CBT-only 提交的 GitHub CI](https://github.com/iChenwin/open-vault/actions/runs/39565292952) 通过静态检查、全仓 race detector 测试和三个程序的构建；不再安装或调用 restic。旧版本的文件备份回归不作为本版 CBT 验收依据。

## 真实内核实验状态

尚未确认通过。已建立隔离 QEMU Ubuntu 24.04 GA 6.8 实验，数据盘均为新建的普通虚拟磁盘文件，未向虚拟机传入宿主机业务盘。

早期基于固件启动的尝试未连接到 guest SSH，串口日志为空，没有执行到块备份，不能记为 CBT 成功。已改用 Canonical 校验过的 matching kernel/initrd 直接启动，并保留串口及 SSH 诊断。直接启动日志已确认 Ubuntu 24.04.5、`6.8.0-147-generic` 内核成功引导、SSH 连通，并进入 guest 编译依赖安装；这些记录仅证明实验环境已启动，不证明驱动编译、加载或备份恢复通过。

最终通过必须同时具备 ext4 与 XFS 的全量/增量 JSON、减少的源读取量、重建镜像与同时间点 oracle 的字节及 SHA-256 一致、文件系统检查、文件清单一致和 `SUCCESS` 标记。对应结果将补充至此文档，未满足前不提供生产支持承诺。

复核发现上游 `v0.11.10` 存在已知 Ubuntu 24.04 XFS 崩溃问题（[问题 #402](https://github.com/datto/dattobd/issues/402)），已将准入版本及新实验固定到包含修复的 `v0.12.0`。旧版实验即使完成，也不能替代修复版验收。

`405c356` 对应的 [0.12.0 实验](https://github.com/iChenwin/open-vault/actions/runs/39540880382) **失败**：驱动在 `6.8.0-147-generic` 编译并加载，但 ext4 lazy initialization 的 zero-write 请求触发 `bio_needs_cow` 空指针异常；全量提交后的增量切换另有 `device busy`。没有执行到完整恢复验收，也未进入 XFS 测试，不能将已提交的全量视为有效验收结果。

后续修复关闭源快照句柄后才切换驱动；增加 Linux 真实文件句柄生命周期测试及 128 代旋转前拒绝测试，均通过。外部构建流程将上游 zero-write 特性宏拼写改为其实际生成的标识，并以 `0.12.0-ov1` 区分 stock 版本；只修改外部 GPL 源码树，保留上游许可。这些修复仍需重新执行真实内核全套实验。

## CBT-only 更新验证

已移除旧文件备份引擎、API、调度器、页面和安装依赖，新增已发布父链的历史版本查询、历史校验和镜像恢复选择。Windows 全仓测试/静态检查通过；Linux 用户态实际执行了 Web/Unix socket、Agent、CLI 协调和脱离原卷的仓库历史查询/校验/恢复测试。Chrome 测试数据检查 1280px/390px 页面、历史选择与校验/恢复请求，未发现运行异常或横向溢出。

补充验证：用户明确选择的恢复版本在后台出现新版本后仍保持不变；超过 256 GiB 的新基线在分配 COW 或执行驱动跟踪命令前即被拒绝。前者通过浏览器测试数据检查，后者通过 Linux 协调器测试。

这些检查不替代内核实验。原生宿主编译只是加速构建，仍必须在隔离 guest 加载、完成两种文件系统的全套恢复比对才能验收。

`e645869` 对应的 [ov1 实验](https://github.com/iChenwin/open-vault/actions/runs/39565285985) **失败**：Ubuntu 24.04.5 / `6.8.0-147-generic` 已加载外部驱动，ext4 512 MiB 全量镜像 SHA-256 一致、只读文件系统检查和文件清单通过；增量只读取源快照 9,068,544 字节，但重建镜像与参考快照 SHA-256 不一致，因此不能算增量恢复成功，亦未执行到 XFS。进一步审查发现增量分支仍用旧宏保护 zero-write 跟踪，ov2 已一并修正并拒绝 ov1；这尚未证明差异原因已完全消除。实验新增差异块位置、COW 物理分配及文件系统诊断，发生差异仍明确失败，不放宽验收条件。

`0fbbf9c` 对应的 [ov2 实验](https://github.com/iChenwin/open-vault/actions/runs/39568439019) **仍失败**，平台相同。ext4 512 MiB 全量恢复比对通过；增量读取源快照 520,192 字节，重建后的只读 `e2fsck` 和测试文件清单通过，但整卷有两个 4 KiB 块不一致：字节偏移 286,265,344 和 286,269,440（块号 69,889、69,890），旧索引映射值均为 0。闭合旧 COW 的最后分配块为 69,888，文件已截断为 1,052,672 字节。这些差异紧邻其边界，符合历史 COW 数据块释放后未被追踪的可能性，但尚未保存截断前分配图，不能将该归因写成完整证明。没有进入 XFS，也不能以文件检查通过替代整卷一致性验收。差异 JSON、原始旧索引、COW 分配、文件系统检查和文件清单均在该 run 的 artifact 中。
